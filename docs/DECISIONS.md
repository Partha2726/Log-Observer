- 2026-10-11: Trace assembly (T12) choices where section 7.1 leaves room. (a) Stage status is computed from OBSERVED lines only, so removing every CORRELATED line never changes it (TRACE-014) and a mis-linked error line can never flip a stage. (b) The first failure is the earliest error line of a failed stage among OBSERVED lines and unambiguous CORRELATED lines (confidence at least 0.8). Lines with a logger (application components) win over status-only gateway lines, because the format A timestamp has second precision and the gateway's 5xx is the consequence. With no error line, the stage's last OBSERVED gateway response of 400 or above is the first failure. (c) Overall status puts FAILED first, then COMPLETED, REJECTED, INCOMPLETE, as the section 4.5.5 note "FAILED wins over COMPLETED" says; section 2.5's list order reads otherwise but would hide failures. (d) Thread expansion skips any candidate that carries a request ID not of this flow, which is stricter than "belonging to another flow": a request ID identifies exactly one other call. (e) Time-only candidates have no thread and none of flowRef, request ID, session ID or user ID; k counts our flow plus the flows owning other lines in the window (by flowRef or request ID). (f) A CORRELATED line takes the stage of the OBSERVED line that pulled it in (the nearest one in its window). An OBSERVED line no matcher or request ID places takes the stage window on its own host, then any host's window, then the nearest window. (g) Session stages are the stages without `actorRole`; their event actions and `signOut`'s drive session expansion and the sign-in fallback. (h) `trace.requester/approver/executor_user_id` hold the actors of the definition's first three roles by position, and every role is in `trace_actor`. Reason: deterministic, industry-neutral, and measured on the fixture: OBSERVED 341/341, CORRELATED 23/23, recall 364/364, all ten flows' statuses and first failures equal to ground truth.

- 2026-10-11: Graph builder (T13) mapping, industry-neutral. Lines of session stages and sign-out lines make ACTOR nodes, one per session (or per user when a line has no session) and direction (sign-in or sign-out). A sign-out node sits in the lane of the latest stage where that user or session acted before signing out. Lines without a logger make one SERVICE node per (service, request ID): in the demo, the gateway's or the auth service's handling of one call. Lines with a logger make one COMPONENT node per (service, logger) in a lane, capped at `maxNodesPerStage` (12); the overflow merges into an "N more components" node that keeps all its evidence. Each external correlation ID makes an EXTERNAL node, labelled with the ID and provider status: the message text that names the payment provider is not stored in Postgres. `call` edges go from the node holding a request's HTTP response line to every other node with that request ID. `integration` edges go from components to EXTERNAL (lines without a provider status) and back (lines with one). A `handoff` source is the last node of the stage that started no later than the next stage's first node, because a session stage holds every actor's sign-in. Node order is by first timestamp, so a gateway node can sort before the component whose exception caused its 5xx (access-log times have second precision). Golden JSON: `backend/src/test/resources/golden/graph-fail-db-timeout-approve.json`. Reason: section 7.6 contract and invariants, with no demo name in code.

- 2026-10-11: Endpoint semantics (T14). Flow search: `from`/`to` (default last 7 days, at most 31) select traces whose `[first_seen, last_seen]` overlaps the range. `stage` + `status` filters on that stage's status, `stage` alone means the stage was reached, and `status` alone is the overall status. `hasAnomaly=true` returns nothing until anomalies exist (phase 2). Unassembled flowRefs come from an Elasticsearch terms aggregation (at most 1,000) only when no stage, status or anomaly filter is set; when Elasticsearch is down, Postgres results are still returned, and 503 is returned only when there are none. Log search stage = the stage the line was linked to in an assembled trace, else the stage its flow definition's matchers give it; the `stage` filter turns those matchers into Elasticsearch conditions (Java path regexes converted to Lucene's implicitly anchored syntax). User activity: sign-in success and sign-out actions come from the flow definitions; failed sign-ins and permission denials come from `app.activity.failed-sign-in-actions` (`LOGIN_FAILED,MFA_FAILED`) and `app.activity.permission-denied-actions` (`AUTHZ_DENIED`). A sign-out line with a request ID is `LOGOUT`, one without is `EXPIRED` (server-side), and no end is `OPEN`; the role shown is the user's first role in definition order. `GET /graph` answers 404 for a trace never assembled; `GET /events` assembles if needed, takes `nodeId` from the graph's evidence IDs, and marks documents missing from Elasticsearch as `expired` (TRACE-033). API-011 and API-012 (anomalies) belong to phase 2 (T22). Reason: section 8.8 leaves these details open.

## Phase 3 (agent run)

- 2026-10-13: OpenTelemetry mode in the generator (T32). `--otel true` (`GEN_OTEL` in Compose) uses the OpenTelemetry SDK 1.66.0 to make one trace per flow (root span `flow <flowRef>`) and one child span per stage, both created when the flow's or stage's first line is written, in simulated time. `opentelemetry-log4j-context-data-2.17-autoconfigure` 2.31.1-alpha puts `trace_id` and `span_id` into each event's context data while that span is current. All three are named in spec section 15.
  - IDs come from a seeded `IdGenerator` with its own stream (seed XOR a constant), so the same seed gives the same IDs and the content streams are untouched.
  - Lines that belong to a flow carry its trace, including the legacy billing lines without a request ID. Noise, incident and scanner lines carry none, as unattached work would in a real system.
  - Format by format (section 15): B gains `trace.id` and `span.id` (a separate JSON template, selected by a system property); C gains `trace=` and `span=` in the `acme@32473` structured data; A gains ` tid=<trace id>` (or `tid=-`) at the end of the line.
  - Format D gains ` trace_id=%X{trace_id}` right after the request-ID column (`| <rid> trace_id=<id> |`). Section 15 gives the token but not its position; inside the header keeps it on the event's first line, which multi-line messages need.
  - With `--otel false` every pattern resolves exactly as before. Verified: a 1,000-flow run, seed 42, with the previous jar and with this one gives identical SHA-256 sums for all 12 files (logs and ground truth). An otel run has the same ground truth and the same lines plus the trace fields (`OtelModeTest`).
